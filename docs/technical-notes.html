1 · What it does

You open the page and talk. Ava (the voice agent) understands the request, reads back anything that would change data and waits for a clear yes. A second agent (the browser agent) then does the job in the EspoCRM web app through a real Chromium browser, streamed live to the caller. One workflow was asked for (create a lead); because the browser agent's tools are generic, the same system also handles other CRM work: edit fields, change status, add notes, create accounts and contacts, link tasks and meetings to records, convert leads, and answer questions ("how many opportunities are in negotiation?"). It does not delete records or run mass actions, by rule.

  • Two agents, two jobs. Ava only converses; she has four tools, all for talking to the browser agent (browser_task, message_browser_agent, browser_task_status, cancel_browser_task). CRM work runs in the background, so Ava acknowledges in her own words ("sure, updating her now"), keeps talking, relays the browser agent's questions, and phrases its result when it arrives. Nothing is hard-coded in what she says.
  • Why not one agent? The voice model must answer in ~0.5 s and stay short; the browser loop needs many tool calls and can take 5–25 s. Splitting them keeps the conversation responsive and gives each prompt one job. An earlier version gave Ava a create_lead tool directly; she once used it to "update" a lead and created a duplicate. Moving all CRM work behind one hand-off removed that class of mistake.
  • Per call: one LiveKit room, one agent process, one Chromium logged in to the CRM. The process exits when the caller hangs up. The server caps concurrent calls (3) and calls per IP (8/hour).

3 · How the agent reads and acts on the interface

Reading: a page outline instead of screenshots

After every action the browser agent receives a compact text outline of the visible page, generated in the page by one DOM walk: headings, field labels with their values, and every visible control with a ref number, its role, accessible name, current value, checkbox state and dropdown options. A lead's detail page is ~1.5k characters. Example:

URL: …#Lead/view/2856681483313ee92        [3] button "Edit" id=edit
# Overview                                  [6] link "1112131415" field=phoneNumber
name: Jane Doe                              [1] checkbox "Contact" checked=no      (convert form)
accountName: ACME                           [24] dropdown "New" field=status → [27] option "In Process"

The model acts by ref (click(3), type_text(13, "…")); refs are re-issued on every outline, and the active element is outlined in purple on the live video so the caller can follow. Text outlines are far cheaper and faster than screenshots for a form-heavy app (each step's model call is ~0.6–1.0 s) and they expose state a screenshot hides (values, checked boxes). Two real failures shaped the outline: dropdown options were invisible (a status change took 26 steps by arrow keys; 11 after options became clickable), and checkbox state was missing (lead conversion looped until 30 steps; 7 steps once the outline said checkbox "Contact" checked=no).

Acting: skills first, generic tools for everything else

  • Skills are scripted Playwright routines for frequent jobs. create_lead types each field visibly using EspoCRM's stable data-name attributes, picks the dropdown, saves, handles EspoCRM's own "might already exist" dialog, then reads the saved detail view and compares every field with the request. search_records queries any entity through the logged-in app's own AJAX layer (same session and permissions as the UI, ~0.4 s) with optional exact filters, after which the agent opens the record so it is on screen.
  • Generic tools (look, click, type, select, navigate, keys, scroll) handle everything else. They contain nothing EspoCRM-specific; the system prompt adds a short map of EspoCRM (where lists, forms and side panels are) and field tips (link fields, dates).
  • Verification. The browser agent must re-read every value it set on the saved record before calling finish(success, summary); Ava only repeats what that summary says.

Everything that changes CRM data happens through the UI. The in-page AJAX is used only for reads (search, duplicate check); evals use the REST API only to set up, verify and clean up test data.

7 · Safety and reliability

  • No write without a yes, in code. Any job with changes_data=true is refused unless the caller's latest utterance is an explicit yes with no correction ("yes, but…" fails).
  • Verified, grounded reporting. The browser agent verifies on screen; every one of Ava's turns gets the real job status injected ("still in progress / finished and verified: … / did not complete: …"), so she cannot claim an unfinished job is done.
  • Ambiguity is asked, not guessed. Several matches → the browser agent asks what tells them apart.
  • Fallbacks: LLM (Vertex → OpenRouter), voice (Fish → Deepgram, with emotion tags stripped), retries with backoff on Vertex 429/5xx (seen in testing on a new project).
  • Resource hygiene: the agent leaves when the caller hangs up; the concurrency cap counts only rooms with a real caller (it previously counted rooms the agent was still leaving, which locked users out).

8 · Limitations and next steps

  • Read-backs of long numbers can be garbled by the LLM even when the saved value is right; a deterministic formatter for phone numbers and emails in the read-back would remove that.
  • Breadth vs depth of testing. 35 dialogues and 16 CRM jobs, not thousands of real calls. Speech-to-text is weak on some Indian names and emails ("Pankaj" → "Bonkers"); spelling recovers it, at the cost of turns. Next: keyterm boosting from CRM names, and replaying real call audio in CI.
  • Browser automation beyond EspoCRM is unproven. The tools are generic, but logins, expiring sessions, unexpected modals and recovering from a wrong click need work. Page text is untrusted input to the browser agent (prompt injection via a record's fields); it can't delete or mass-update, but a production version needs an allowlist of actions and per-tenant review.
  • Latency. Speculative LLM start on Flux's early end-of-turn signal; a faster voice (ElevenLabs Flash is ~0.15 s vs Fish ~0.25 s); skills for more frequent jobs (scheduling) to cut 20+ s jobs to a few seconds; a learned skill library where the generic agent records a successful path and later replays it.
  • Scale. One VM, one Chromium per call (~3 concurrent calls), free-tier limits (LiveKit: 5 concurrent TTS connections, $2.50 inference credit). Next: browser pool, autoscaling workers, monitoring and alerting.
  • Product. Phone numbers (LiveKit SIP), caller authentication, data-retention policy for call logs.
